How I cut API latency 40% for 150K+ daily users

p95 went from about 1 second to about 200ms. The work was diagnosis first, then cache, indexes, and a safer deploy path — not a rewrite.

150K+Daily active users
0User-facing downtime during cutover

The problem

Hot paths in a NestJS/Node.js financial API were spending most of their time in the database and in repeated reads of slowly changing reference data. Under 150K+ DAU that showed up as p95 near 1s — enough to stall onboarding, balances, and statement flows.

How I found it

  • Traced slow handlers with OpenTelemetry and CloudWatch — the bottleneck was data access, not CPU.
  • Logged query shapes: unindexed filters, repeated lookups in loops, and aggregations that scanned too much of MongoDB.
  • Separated “must be strongly consistent” (ledger, auth) from “can be cached for seconds” (profile flags, product config, watchlist metadata).

What we changed

  • Redis in front of read-heavy, low-churn data, with short TTLs and explicit invalidation on writes.
  • PostgreSQL indexes matched actual WHERE/JOIN patterns, not guesswork from the schema.
  • MongoDB compound indexes and aggregations rewritten so the working set stayed in RAM for the hot collections.
  • AWS ECS blue-green deploys so the index and cache changes rolled out without a freeze window.

What I would still watch

Cache stampede on expiry, stale reads on KYC status, and index bloat. We kept ledger posts and disbursement writes on the primary path — no cache in front of money movement.

This is the public version of production work. Vendor internals and customer data stay private. The numbers match my resume: 40% latency cut, 150K+ DAU, 5M+ monthly transactions on the same platform.
